# TF3 track geometry mod: game reference

What the code, documentation, and git history cannot tell you: the game's API, its gotchas, and what was found in game or reverse engineered.

Lua API documentation can be found at: https://wiki.transportfever3.com/script-doc/

- The game reads the mod only from the staging copy (`./sync.sh`). When testing the mod in game, reloading the map will reload the mod as well. No need to restart the whole game.
- **A new script file needs a game restart** (seen in game 2026-11-20; a restart fixed it): synced edits to existing files load on the next map load, but with a new `.script.tl` added while the game ran, the next map load crashed on `module 'track_geometry_tool::/track_geometry/<file>' not found` from the first `require` of it (the file was in the staging copy). The game seems to list a mod's files at launch.
- The geometry core is a port of the Lean code. `test/fixtures.lua` comes from `lake exe fixtures`: **regenerate it after changing the Lean core.**

## Found in game

- **Tightest radius the game builds**: 40 m (found by experiment).
- **Overlapping pieces**: a new piece may overlap existing track only where it shares a node with it; one that does not is refused ("Construction Not Possible", no collision shown). The game's own builder lays the whole diverging part of a switch as one piece (so its 4 km switches build). Switches off straights split into 20 m pieces were refused: the second piece still ran within a metre or two of the main line. A shallow branch that overlaps the track it leaves past that track's next joint is refused too (refused with the joint 0.4 m off the branch's centre line; built with it 1.7 m off). Merged pieces of 310 m and 353 m (a crossover between tracks 5 m apart) build. (Is this true? I'm not so sure.)
- **Switches replace the pieces**: the game's own builder removes and re-adds the pieces at a switch in the same build (they light up in its ghost). Clones (`BaseEdge:clone()`) in `edgesToRemove` plus `edgesToAdd` build; so does a cut piece replaced by its two Hermite halves (tangents scaled by u and 1 − u). Not tried: a node end without replacing its pieces, and pieces carrying signals or other edge objects.
- **The game's builder branches** off a straight at a radius of about 182 m.
- **Menu rows on the game's track entries**: a row with `preserveValueInAllCategories` keeps one value for every entry and category. The game's builder greys the Snapping row while Shift is held, and joins nothing when Snapping is No. Its snap toggle key (`constructNoSnap`, C) belongs to its builder's action, so it does nothing in another action. `construction_react_util.forEachDefinition` runs after every mod's `getTrackDefinitions` wrapper, so wrapping each row's `checkEnabledFn` there reaches rows added by mods that load later. Real Track Cant and parallel tracks both add their rows by wrapping `getTrackDefinitions`; parallel tracks also adds rows in `getActionParams` when that wrapper missed an entry.

## Building track (proposals)

- Build an `api.type.SimpleProposal` and fill `streetProposal.nodesToAdd` / `edgesToAdd`. **Fill plain Lua tables and assign each list whole.** Reading a list field returns a copy, so `sp.edgesToAdd[i] = e` is silently lost and the proposal builds nothing at cost 0.
- New entities take negative ids: edges `-1..-m` first, then nodes `-(m+1)..`. Use an existing node's entity id to attach to it.
- Node: `NodeAndEntity.new()`, with `entity` and `comp.position`.
- Edge: `SegmentAndEntity.new()` with `type = 1`. It needs `node0/1`, `position0/1`, `tangent0/1` (a cubic Hermite: tangent scaled by `T`, z = slope × T), `type = BaseEdgeType.NORMAL` (`typeIndex = -1`) or BRIDGE/TUNNEL with a type id, `roadType = TRACK`, `roadTemplate`, `laneConfigs`, `roadStyle = template.streetStyle`, `distance = template.trackDistance` (without it, embankments break), and `playerOwned`.
- Edges are only Hermites. `EdgeGeometry` ARC is for drawing only.
- **Town buildings in the way** (probed in game, 2026-11-17): `Context.gatherBuildings` takes effect only in a dry run (`makeProposalData`) or a build; **`ProposalViewer` takes no `Context`**, so the ghost's check lists the houses as collisions (their `TOWN_BUILDING` entities, each twice) and its cost leaves the demolition out. A dry run with `gatherBuildings` drops them from `collisionEntities`, warns `N Buildings Will Be Removed`, and adds the demolition to `costs` (e.g. 74 k → 425 k for 2 houses), but leaves `buildingEntities` empty: it does not say which houses go. A proposal's own `constructionsToRemove` takes a town building's construction (`TownBuilding.construction`), as Auto Track Connector uses it. The viewer's check of such a proposal counts their demolition in `costs` (seen in game: 14 k → 465 k for 2 houses). **The viewer's check lists only some of the houses in the way** (2 where the dry run warned of 8); with those in `constructionsToRemove`, the next check lists more (4 others).
- **Building with houses in `constructionsToRemove` kills the game**: a build naming 8 houses there failed the assertion `m_removedTnEntities` has duplicates (`SimEntityUpdateHelper.cpp:2013`), with `gatherBuildings` both true and false (seen in game twice; dry runs of it do not crash). Probably houses along one street share transport-network entities. Build with the houses left out and `gatherBuildings = true`, as the game's own builder does: its dry run of the same track gave no errors and no collisions. Its cost differs too: the dry run with `gatherBuildings` priced 8 houses at 1.84 M, the viewer's check with them in `constructionsToRemove` at 3.42 M.
- **Finding the houses on the map**: `api.engine.system.octreeSystem.findIntersectingEntities(Box3, fn(entity, BoundingVolume))` gives every entity with a box in the area, with its axis-aligned `bbox`; town buildings are the ones with `TOWN_BUILDING`. Their boxes are loose: 3 houses within 3 m of a track's centre line by their boxes, and the game removed none of them (seen in game).
- **Which houses go, by count**: a dry run with `gatherBuildings` warns `N Buildings Will Be Removed`, and each house in the way that the proposal already names in `constructionsToRemove` makes N one less (8 → 6 with 2 named, seen in game).
- **A dry run without `gatherBuildings`** is taken to name the houses in the way as collisions, a few at a time, as the viewer's check does (not yet seen in game: the dry runs logged in game, 2026-11, all gathered).
- **Roads a proposal crosses are not split**: the engine leaves a crossed street as a collision, with or without `gatherBuildings` (`old2new` stays empty).
- **Cutting a street** (from Auto Track Connector and Network Tools; seen by us in game: level crossings built that way): a street part is a `SegmentAndEntity` with `type = 0` and the old piece's `BASE_EDGE_STREET` as `streetEdge`. The lane rules (`BASE_NODE_CONFIG`) at the street's nodes name its pieces: one naming a removed piece kills the game ("lc.segment0 not found", `StreetShapeFactory`), even in a preview. So the node goes into `nodeConfigsToRemove`, and its own config, with the piece renamed to its part there, into `nodeConfigsToAdd`; removing it without adding it back crashed later ("it != components.end()", `BaseNodeConfig`). A new node in `streetProposal.node2rcType` (node -> `railroadCrossingTypeRep` id) is a level crossing; a level crossing at the node of a removed piece is made again the same way, of its own type (`RAILROAD_CROSSING.typeIndex`, on the node or an entity listing it).
- **Level crossings the game refuses** with a bare "Construction Not Possible" (critical, no collision named), from leave-one-out dry runs in game: a road piece left next to a joint or a road's end under about 6.5 m (2.0 to 6.4 m refused, 6.5 m built); next to a junction of three roads or more under about 16 m (5.8 to 13.1 m refused, 16.1 m built); a track piece left 3.2 to 3.8 m long; a road crossed at 10 to 24 degrees (65 and over built). Next to an existing level crossing 10.1 m built. Two pieces of one road can be joined across their joint as Move It and Network Tools do: one Hermite from far node to far node, tangents along the far ends as long as both pieces, the joint in `nodesToRemove`. The joint's lane rules go with it; Move It found that listing the joint in `nodeConfigsToRemove` as well trips an assertion ("map_util Get"). Precedence is per end (`BASE_EDGE_STREET.precedenceNode0/1`), so each end of the joined road takes it from the piece that had that end. A component read with `getComponent` is read-only ("cannot write to read only member 'precedenceNode0'"); write the copy on the `SegmentAndEntity` after assigning it, as Parallel Tracks does.
- **Diamond crossings**: existing track crossed at grade is cut like a road at a level crossing: its piece replaced by clones of its `BaseEdge` (`SegmentAndEntity.type = 1`) meeting the new piece's parts at a shared node, with no `node2rcType` there. The engine takes it (in game, 2026-11-18). Double track 5 m apart builds with both tracks cut, leaving a 5 m piece of the new track between the two diamonds. There is no track edge component: catenary comes with the track template (`catenaryAdd`/`catenaryRemove`).
- Dry run: `api.engine.util.proposal.makeProposalData(proposal, context)` gives `costs`, `errorState`, `collisionInfo`. Build: `api.cmd.sendCommand(api.cmd.makeWorldBuildProposalCmd(p, ctx, false, true), cb)`, sent from the GUI.
- **Crash traps** (fatal, `pcall` won't catch them): naming a node that no longer exists, NaN coordinates, pieces under 0.1 m. Validate before every preview or build.
- **The builder's own proposals can be watched** (seen in game, 2026-11-19). A game script (`.gs.lua` with `updateScript` and `guiHandleEventScript`) calls `state:subscribeToEvent("builder.proposalCreate")` and `("builder.proposalApply")` in its `update` (without the subscription nothing arrives; the earlier probe that saw nothing did not subscribe) and gets `guiHandleEvent(userParams, state, guiState, src, id, name, param)` with `id = "trackBuilder"` and `param = {Proposal, ProposalData, result}`, for every preview (`proposalCreate`, new entities negative) and build (`proposalApply`, after the build: real ids, and a removed entity reads "Invalid entity") of the game's own tool. Real Track Cant, Advanced Track Patterns and Parallel Tracks do this. A plain-Lua script file needs a global `data()` returning its table, or the game logs "Expected table at path" every tick. A string returned from `guiHandleEvent` vetoes. Our probe (deleted; it was a few dozen lines logging the Proposal and ProposalData per event) is easy to write again from this.
- **What the game's own track tool proposes** (read with that probe): *Bare refusals*: 8 of 10 previews were refused as "Construction Not Possible", critical, cost 0, no collisions, no buildings, nothing else in `ProposalData`. So the engine's refusals are as vague for the game's own tool as for us, and there is no reason to find in the data. *Crossed street*: cut into two new street parts (type 0, `lanes` 4, `playerOwned` false, precedence 2/2) that share one new node with the track; the old end nodes go into `nodeConfigsToRemove` and come back in `nodeConfigsToAdd` with the new node. The build then has a `RAILROAD_CROSSING` entity at that node (`railRoadCrossingSystem.getRailroadCrossingForNode`: `typeIndex` 0, 1 node, no edges), though `node2rcType` reads as empty on the proposal it hands to scripts, so a script cannot see the crossing type there. *Crossed track*: the same cut, with no crossing entity (a diamond); across 5 parallel tracks it left 5 m pieces of the new track between them. *Track pieces*: up to about 90 m each (chords of 80 to 96 m), split again at every crossing node. *Bridges*: chosen by the tool (`type` BRIDGE, `typeIndex` 4 on a rise to about 11 m). *Houses*: each house in the way is its CONSTRUCTION in `proposal.toRemove`, already in the preview (4 in one, with the warning "4 Buildings Will Be Removed" and the demolition in the cost), and a build with 7 and one with 10 did not crash. `toRemove` holds only those constructions: removed road and track pieces go in `removedSegments`. This does not explain why our build naming 8 houses crashed (above); not found.
- **Who fills in the houses** (tried in game, 2026-11-19): the `Proposal` that `ProposalViewer`'s `onCreateProposalData(data, proposal)` hands back only echoes our own `constructionsToRemove` (14 houses from our footprint, and 18 after our search added 4: those 4 were not in what the viewer returned). The game's own tool names them from its C++, which no script call reaches. **`makeProposalData` takes a `SimpleProposal` only**, though its Teal definition says `Proposal`: it throws "bad argument #2 to 'makeProposalData' (SimpleProposal expected, got Proposal)", and each throw costs about 300 ms. So a gathering dry run could not be tried on the viewer's `Proposal`; `makeWorldBuildProposalCmd` has both overloads (not tried with a `Proposal`).
- **Reading a refusal in the log**: `agent-scripts/tflog 'refusal#'` shows every refusal as numbered lines (`refusal#<n> <log point>:`): the header (cost, critical, `bare` when it is "Construction Not Possible" with nothing named), one line per non-empty message list, one per entity the game names (collision, building, auto-removal, removable module) with its position and our nearest piece (index along the path, distance in m, to the chord between plan nodes), then our own account of the track (path, crossings cut or not and why). Log points: `ghost` (`ghost mid-drag`), `house search`, `build check`, `build`. A bare refusal has nothing more in `ProposalData`; the account is the only lead. No new game refusal messages seen yet; add them here when seen. Seen in game: the game lists one entity once per piece it meets (the log counts them, `(x3)`); long tracks through town list `auto-removal` entities that have only BOUNDING_VOLUME and MODEL_INSTANCE_LIST (no town building, construction or edge), placed by their box's centre. A `collision` with only BOUNDING_VOLUME sits at round coordinates (-384.0, -38.4; -640.0, -76.2) 25 to 92 m from our nearest piece: likely a large box (a map tile or a group), so its centre says little. Refusals now log each entity's box. Seen: a `subconstruction` collision with a box 238 by 276 m (z 4 to 31) whose centre is 40 m from our nearest piece, so a collision with such an entity is with part of a large box (the entity is not at its centre).
- **Finding the section a bare refusal comes from** (`refusal#<n> search:` lines in the log; the algorithm is in tg_proposal). Not yet seen in game: how long the search stalls (each dry run blocks its frame, 50 to 300 ms for a long track, about 2 log2 n + 1 runs) and which bare causes it finds. A section is laid out without the switches' copies and merged runs, which belong to the whole path only.
- Reading track: `getComponent(e, BASE_EDGE)`; `streetSystem.getNodeStreetSegments(node)`. `forEachEntityWithComponent` refuses BASE_EDGE.
- The proposal's `comp.type` is taken literally: no bridge or tunnel unless asked. The game's drag tool picks them natively (track: bridge above 6 + 6 m, tunnel below 9 + 6 m), and the menu auto-selects types in `menu_category_util`.
- `ProposalData.entity2tn` gives each proposed piece's transport-network edge, and its `curveSpeedLimit` (m/s) is the game's own curve speed. The Speed Limit layer only paints built track.
- **How the game's builder eases grade** (reverse engineered): one Hermite per drag with `z'(u) = e + (s0 − e)(1 − u)²`, with no vertical-curve minimum. Templates have `maxSlopeBuild = 0.085`, `maxSlope = 0.13`, `maxSlopeShape = 0.16`.

## Tool and GUI

- **Hosting a tool on an entry**: an entry's custom-action recipe calls `params.setActionFn(fn, key)` while `isActive`, and `fn` returns `builtin.ActionDescriptor{ tool = "construction", children }`. A tool with a menu entry of its own is a `.res.lua` of `type = "construction_tool"` whose `getDefinitionFn` returns `{ action = "ACTION_CUSTOM", customAction = { recipe }, menuCategory, params }`. A row's `tooltip` is shown as given, with no line breaking: break it with `\n`.
- **A custom action on the game's own entries**: the construction menu runs `definition.customAction.recipe` for any entry, whatever its `action` (`construction.tl`). It runs the recipe for every entry it shows, not only the picked one, and `isActive` is true for all of them with a mouse (it is false only in gamepad mode before the entry is applied): in a test the recipe bound the tool for all six track entries at once. `setActionFn(fn, key)` is kept per definition (`bindActionFn`) and only the picked definition's `fn` is used (`propagateActionFn`); `setActionFn(nil)` drops it and the menu falls back to the entry's own action. So anything that depends on which entry is picked is set inside `fn` (`hostedAction`), never in the recipe body. Bind every entry under one key. The tool stack (`ToolStackEntryWrap`, `builtin.lua`) keeps the action's node and only swaps the `fn` while the key stays; it runs the new entry's `fn` (seen in game). A new key builds a new node, and the new action mounts before the old one unmounts, so state shared between them is torn down by the old one's unmount. The recipe on an entry also brings the menu item's own custom-action handling with it even while nothing is bound (it aborts the action when its tab is hidden; gamepad apply/back). The track entries come from `construction_react_util.getTrackDefinitions`, which a mod wraps from a `react-plugin ::ModEntryPointExtension` (as Real Track Cant does).
- **A Button row's labels are cut off, not wrapped or shrunk**: the buttons share the row's right half, so two buttons fit about 7 characters each ("Horizontal" showed as "Horizon", seen in game). Keep labels short.
- **A row's values**: a row with `numbers` reports the picked number (Track Geometry: 0, 1); one without reports the index (the `mode` tabs: 1 build, 2 Replace Track). The panel calls each row's `checkEnabledFn` with all the panel's values on every look, the only place a custom action can read them: `getCurrentParams` gives it only the Settings window's.
- Children: `builtin.Selector{ onProcessMouseEvent }` takes raw mouse events (return true from `Pressed` to keep the camera off a drag). `builtin.ProposalViewer` draws the ghost, and **only one may exist at a time** (a second is fatal). `EdgeRenderable` draws gizmos (STRAIGHT or ARC, `angle = 2π` for a circle). `builtin.FullScreenComponent` hosts the badges.
- `getCurrentParams` returns only the Settings-window params (`location = Default`). Params are option switches only, with no one-shot button.
- **The game runs Lua 5.2.** Use `math.atan2`, since two-argument `math.atan` ignores `x`.
- A file's main chunk allows at most 200 locals, and each Teal record counts as one.
- Requires: `ug_require "::/gui/main/react.lua"` for game GUI; `require("<modId>::/path/file.script.tl")` for our own. **`ug_require` works only while a script loads** (at a module's top level): the game's `require` (base/init.lua:103) resolves the path against the file being loaded, and called later (from a tool's tick, say) `resolveutil.resolve` throws "Invalid number of parameters" (seen in game, 2026-11-18).
- A share of `getCameraData()[3]` (the camera's distance) stays constant on screen.
- Shift: `api.gui.inputAction.modifierOnlyActionIsActive("IA_PRECISION_MODE")`. Ctrl + left drag belongs to the camera.

## GUI pitfalls

- **`os.clock()` is CPU time summed over threads**, not wall time. Count tool ticks or frames instead. `api.type.Clock` (`new()`, `getTime()` in µs) measures wall time (its frame rates matched PerfMon's).
- **Restricted outside a game-bar plugin's `react.onStep`**: `api.gui.mouse.getTerrainPosition` and `api.gui.camera.world2Screen` return "API is currently restricted". `TgProbe` reads them (and `getEye`) there and hands them over. `terrain.getHeightAt` and `isOnWater` work anywhere.
- **Right-click / Esc**: both arrive as "back". The tool never sees the right press (the camera keeps it). It sees the release, and "back" comes only after a still click. "Back" goes first to the `IA_CLOSE_TOPMOST_WINDOW` / `IA_MENU_BACK` handlers on the keyboard focus's path, and only when none takes it to the action's `onBack`. `onSelectSecondary` never fired (seen in game). A right-click's "back" comes in the same frame as its right-button "clicked" mouse event (a press shows up as "other"), so that event marks the next "back" as a right-click, once and for at most a tick. (A 0.4 s window after a right-click instead ate quick presses and took an Esc for the click.) `onSelectSecondary` claims a right-click but never acts, or its "back" would be taken for an Esc. Capture `IA_CLOSE_TOPMOST_WINDOW` so the construction menu stays open.
- **The menu keeps the keyboard focus** once a track entry is clicked in its list, even after the tool closes and reopens. "Back" then reaches the menu's `IA_MENU_BACK → quit`, and every Esc and right-click closes the tool (seen in game: until the map was reloaded). Clicks in the world do not take the focus back. `focus()` on a node in the action does nothing (the tool stack is not focusable), and a handler in the entry's custom-action recipe is not on the focus path. A game bar plugin can take it: `TgProbe` (`setForceFocusable(true)`, `useSelfRef():focus()`) takes the focus when the tool opens, on each left press and after another entry is picked, and its `IA_CLOSE_TOPMOST_WINDOW` handler, enabled only while the "back" is the tool's, takes every Esc and right-click (seen in game). One press can come both by a handler and by `onBack`, so each counts once a frame.
- **Esc that is not the tool's own must close the menu itself.** A custom action's `abort` does not close anything in mouse mode: `deactivateAction` re-propagates the same entry, which opens the tool again. The game leaves Esc to the menu's `IA_MENU_BACK → quit`, but that sees the key only while the keyboard focus is in the menu; after a click in the world, Esc reaches only the action's `onBack` (seen in game: `abort` ran on every press and the tool stayed open; our `IA_CLOSE_TOPMOST_WINDOW` state fn was never even polled). So `onBack` also fires `api.gui.fireReactEvent("constructionMenuQuit")`, the event `quit` raises (construction.tl), which pops the construction tool. `fireReactEvent` is missing from the tealdefs: cast it.
- **What a ghost costs the game** (seen in game, 2026-11-18, a 5.7 km track through a town): the game's handling of each new `ProposalViewer` held up one frame for 90-160 ms, even for a ghost of about 20 pieces, with the mod's own work already done in earlier frames (about 130 ms for one of 5.8 km). That frame comes after the check's data (`onCreateProposalData`) arrives, so it is the game handling the ghost, probably drawing it, and the mod cannot split it. A dry run (`makeProposalData`) of a 5.8 km proposal blocks its frame for 50-300 ms. Coroutines exist (`coroutine` is there in the GUI script, as Auto Track Connector uses it) but share the game's thread: a game call blocks its frame wherever it runs. `octreeSystem.findIntersectingEntities` reports every tree and asset in the box, not just edges and houses.
- **So: a sketch while moving, a ghost at rest.** While the mouse moves a path (a drag, and picking the end) the tool draws it as its own line (`EdgeRenderable`), never a `ProposalViewer`; the ghost comes only at rest, made in one frame, one hitch each. The tool's redraw key must change with the ghost's kind (sketch or ghost), or a ghost made for the same key as the last is never drawn.
- **A game call that throws costs about 300 ms, even inside `pcall`** (seen in game, 2026-11-18): the game logs each one as a C++ exception with a stack trace ("Exception type: Lua exception ... ThrowUncheckedImpl"). Never retry a failing call per ghost or per frame: remember the failure. In the GUI script, `ug_require "::/gui/main/menu_category_util.tl"` plus `getAvailableObjectsSorted(api.res.railroadCrossingTypeRep, year)` raised "Invalid number of parameters" (Loader.cpp:278), and `tg_world.crossingType` asked again for every ghost: that was the 320 ms stall at each ghost of a long track. Count the log's "Error message:" lines after a drag to find any others.
- **Picking on bridges**: the ground under the mouse lies far behind a raised track, so pick along the view ray (`getEye()` through the ground point).
- **A window recipe must wrap `builtin.Window`** with `react.RegisterWrapperRecipe`, or it fails `NodeStorage.cpp:51`. **Opening a window from `onStep` crashes** with the same assertion. Open windows from a click via `windowContainer:get():getApi().addSingletonWindow`. A menu row's `onChangeFn` counts as a click: the Alignment row opens and closes the Elevation window from it (seen in game). `ToggleButtonGroup` indices are 1-based. A window gets its params once, so poll the session with its own `useStepStateTimer`.
- **Badges layout**: the full-screen recipe must return a layout (a `Component` kills the GUI with "Recipe child must be a layout"). It shrinks to its children unless `tg_gui.css.lua` sets `gravity = {-1, -1}`. `size` in `meta.styleSheet` is ignored, and inline styles have no `gravity`. There is no text HUD primitive. A `FloatingLayoutChild`'s `h, v` (0..1) is an alignment, not a corner: the child's own point at `h, v` sits on the layout's point at `h, v` (the game's construction menu puts a count in the bottom right with `h = 1, v = 1`; `-1` fills). So a child of size `cw x ch` at top left `(x, y)` takes `h = x / (W - cw)`, `v = y / (H - ch)`. A later child draws over the earlier ones, and of overlapping `builtin.Button`s the one on top takes the click (seen in game, 2026-11-20).
- **`world2Screen` returns whole pixels** (`Vec2i`). From far off a metre is a fraction of a pixel, so a direction read from points a metre apart is noise that jumps with every camera move (seen in game: the badges jumped). Read it over enough metres to span many pixels (`readout.screenFrame`).
- The builder's native tick/cross is `BuildControlComp` (C++ only). Its icons are in `gui/construction/build_control/`.
- **Mouse cursor**: `ActionDescriptor{ mouseCursor = id }` sets it while the tool is active. The Teal def leaves the field out, but the game's own construction tools pass it (`construction_react_util.tl`). Ids are in `gui_react_util.tl` (`getMouseCursorInteger`): "Rail" = 1024 is the track builder's (seen in game).
- **Control point** (the builder's white dot, with a blue ring while dragging): `ProposalViewerParam.controlPointInfo = builtin.type.ControlPointInfo.new(Vec3f pos, offsetZ, radius, State)`, State one of Normal, Hover, Dragging, Idle, IdleOverEdge. One per viewer; a viewer with an empty `SimpleProposal` holds one too. Seen in game: Normal a grey dot, Hover a grey dot ringed blue, Dragging a white dot ringed blue, Idle a white ring, IdleOverEdge a blue ring, Invalid nothing. The road builder uses Idle (ground), IdleOverEdge (over track or road) and Dragging. How the game draws it (reverse engineered, `builderRendererUI`, around `0x11ef110` in the binary): screen-space round sprites, D = 12 px × UI scale across. Normal: a D dot of grey 0.75. Hover and Dragging: a 2D disc of blue (40, 91, 123) under a D dot, grey 0.75 for Hover and white for Dragging, so it reads as a ringed dot. Idle and IdleOverEdge: one dot, white for Idle and a style colour (the renderer's own field, not settable) for IdleOverEdge, of diameter min(D, 2D − p), where p is `radius` projected to pixels. So the dot shrinks as the radius grows on screen and is gone past 2D. With radius 0 it is a full solid dot, which is the track builder's look. `offsetZ` and `radius` are ignored by the other states. C++ also has states 6 and 7 (more style colours), which the Lua enum does not expose.
- **Untested in game**: the elevation box (whether `DoubleSpinBox` follows a new `value` and fires `onValueChange` for it, and whether typing digits fires game hotkeys; if so, try `inputActionBubbleUpFilter = filterOutAll()`). The mode window's Curve section: the same `DoubleSpinBox` questions as the elevation box; whether the curve badges as `builtin.Button`s take the click, and whether the default button skin hides the badge's colour; whether a short test arc reports the limit a long built curve does.
- **The game's curve speed** (`curveSpeedLimit` from dry runs of 80 m test arcs, seen in game 2026-11-20): the same on simple and standard track at a radius (100.0 km/h at 304.1 m, 147.1 at 606.5 m, 770 at 20 km); faster on high-speed track (186.2 km/h at 606.5 m, 168.4 at 514.2 m, 100 km/h at about 216 m). The value is read before the track's top speed caps it. A test arc overlapping existing track still gets its `curveSpeedLimit`. No API gives radius to speed: only a dry run of a piece does.
- **The readout while the path moves is approximate.** A sketch has no ghost, so no game check and no `curveSpeedLimit`; its curve speeds are the speed probe's lookup (`readout.sketchSpeeds`). It also plans without ground or water, so it has no bridges or tunnels. The settled ghost's own check replaces it. One dry run per drag tick did not stutter in game (dragging turns on a 4-turn, 5.6 km path), so the radii are not bucketed; the cost was judged by feel, not timed.
