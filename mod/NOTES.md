# TF3 track geometry mod: research notes

Goal: an in-game tool that lays **new** track between two existing track segments (picked like in Auto Track Connector). The alignment starts as the connection between them. The player splits it by adding **turns** (horizontal PIs) at chosen spots, then drags them and resizes each curve with brackets. A separate set of **elevation PIs** controls the vertical profile, which never follows the terrain. The player previews the result, can pick a different alignment, and then builds. Built track is ordinary game track, so to change it you destroy it and rebuild. The geometry core is ported from the Lean code (`TrackGeometry/*.lean`) to Teal, with the Lean code serving as the spec.

## Lean → Lua

There is no Lean 4 → Lua backend. Lean compiles only to C/LLVM, and a custom backend would mean writing a separate executable that consumes `.olean` files. So we **port the core by hand** (Vec, Segment/clothoid sampling, corner solve, `buildPath`). `Cant.lean` is not ported: the mod builds without cant, and the centreline code does not depend on it. The `RFloat` instance is the reference for numeric behaviour.

## How track is built (from Auto Track Connector)

See `6429593/content/track_connector/tc_proposal.script.tl`, `proposals.makeProposal` (~L395–640).

- Build an `api.type.SimpleProposal`. Fill `proposal.streetProposal.nodesToAdd` / `edgesToAdd` (also `edgesToRemove` and `nodeConfigsToAdd/Remove`, which we don't need for new track).
  - **Fill plain Lua tables and assign each list whole** (`sp.edgesToAdd = edges`). Reading a list field off the native proposal returns a copy, so `sp.edgesToAdd[i] = e` is lost. The proposal then stays empty, and the dry run and the build both "succeed" with cost 0 and nothing built.
- New entities use **negative ids**: edges `-1..-m` first, then nodes `-(m+1)..`. To attach to existing track, use the existing node's entity id for `node0`/`node1`.
- Node: `api.type.NodeAndEntity.new()`, set `entity` and `comp.position = Vec3f`.
- Edge: `api.type.SegmentAndEntity.new()`, set `type = 1` (track) and these `comp` fields:
  - `node0`, `node1`, `position0`, `position1`
  - **`tangent0`, `tangent1`**: each edge is a **cubic Hermite**. Tangents are scaled by a length `T`, and their z-component is slope × T.
  - `type = BaseEdgeType.NORMAL` with `typeIndex = -1`, or BRIDGE/TUNNEL with a bridge/tunnel type id
  - `roadType = RoadType.TRACK`, `roadTemplate = <track template name>`, `laneConfigs = template.laneConfigs`, `roadStyle = template.streetStyle`
  - `distance = template.trackDistance` (5 m). Without it, embankments and noise barriers break.
  - `e.playerOwned` with `owned.player = api.engine.util.getPlayer()`
- Templates: `api.res.streetTemplateRep.find(name)` / `.get(id)`.
- Tangent length for an arc-like Hermite piece (`tc_planner.script.tl` `planner.tangentLength`): with chord `c` and turn `φ`, `r = c / (2 sin(φ/2))` and `T = 4 r tan(φ/4)` (`T = c` if φ ≈ 0).
  - **Consequence for us:** there are no native clothoids, so we sample our alignment into short pieces with exact position and heading at every node, and the Hermite fills in between. Piece length decides accuracy, especially through spirals.
- Dry run (cost, collisions, errors) with no building: `api.engine.util.proposal.makeProposalData(proposal, context)`, then read `data.costs`, `data.errorState.{critical,messages,warnings}` and `data.collisionInfo.collisionEntities`.
- Build: `api.cmd.sendCommand(api.cmd.makeWorldBuildProposalCmd(proposal, context, false, true), callback)`. Track Connector does this from its **game script** (`tc_engine.script.tl`, registered via `track_connector.gs.lua`). The GUI sends it events with `api.cmd.makeScriptingSendEventCmd("", "TrackConnector", name, param)`. The GUI can also send the build command itself (as the Move It mod does), which is what we do.
- Crash traps they hit (the game dies; `pcall` won't catch it):
  - a proposal that names a node that no longer exists
  - NaN coordinates
  - zero-length pieces (< 0.1 m)

  Validate before every preview or build.
- Reading existing track: `api.engine.getComponent(e, api.type.ComponentType.BASE_EDGE)` gives node0/1, position0/1 and tangent0/1. `streetSystem.getNodeStreetSegments(node)` lists a node's edges. `forEachEntityWithComponent` refuses BASE_EDGE.
- Terrain under the mouse: `api.gui.mouse.hasTerrainPosition()` / `getTerrainPosition()`.

## How the tool / UI works (from Auto Track Connector)

- **Registering a tool:** a `.res.lua` with `type = "construction_tool"` and `getDefinitionFn` pointing at a function. That function returns `{ name, icon, action = "ACTION_CUSTOM", params, menuCategory = { categories = {{ category = "rail_tools" }} }, customAction = { recipe = <React recipe> } }`. See `tc_gui.script.tl` `TcToolDefinition` (~L4811).
- **Tool body:** a React recipe (`react.RegisterRecipe`) that returns `builtin.ActionDescriptor{ tool = "construction", onBack, children = {...} }` (~L4516–4630). Its children:
  - `builtin.Selector{ onHover, onSelect, onSelectSecondary, filter, onProcessMouseEvent = function(evt) ... }`. This takes raw mouse events (`evt.button`, `evt.type` = Pressed/Released/Clicked). **Use it for dragging control points.**
  - `builtin.ProposalViewer{ simpleProposal, onCreateProposalData, proposalId, entityForRefundableContext }` shows the game's see-through **ghost** and reports cost and errors. **Only one ProposalViewer at a time**; a second one is fatal.
  - `builtin.ActionTooltip(...)` for the hint text at the mouse.
- **The menu recipe** (`customAction.recipe`) gets `ConstructionCustomActionParams` (`isActive`, `abort`, `setActionFn`, `getCurrentParams`). While `isActive`, it calls `params.setActionFn(fn, key)`, and `fn` returns the `ActionDescriptor` that puts the tool in the world. The recipe itself returns nil. The game's own version is `construction_react_util.RegisterCustomSelectorBasedActionRecipe`.
- The game's GUI sources (`construction_react_util.tl`, `builtin.lua`, the built-in tools under `gui/construction/tools/`) are in `<install>/base/content/gui.zip`.
- Per-frame tick: `engine_react_util.useStepStateTimer(fn, 0.05)`, or `react.onStep`. **The ground under the mouse (`api.gui.mouse.getTerrainPosition`) can only be read from a game-bar plugin's `react.onStep`**; the tool's own timer is refused. Track Connector reads it there and hands it to the tool through module state.
- Right-click and Esc are the same "back" input. The right button arrives as a mouse event just before it, so a "back" within `RIGHT_TICKS` tool ticks of a right-click is that click. While picking ends, right-click steps back and Esc closes the tool. While editing, right-click acts only on the turn under it; Esc steps back. One input's "back" can arrive more than once (selector, input action, `onBack`), so after acting the tool swallows further ones for `RIGHT_TICKS`. Capture it with `IA_CLOSE_TOPMOST_WINDOW` so the construction menu doesn't close itself. **The tool never sees the right press** (right-drag moves the camera and keeps it); it sees the release, and the game sends "back" only after a still click, not after a camera drag. So the tool acts on that "back": while editing it removes the turn under the mouse. (Found by logging every right-button event in game, v23.)
- **The game runs Lua 5.2.** Two-argument `math.atan(y, x)` ignores `x` there; use `math.atan2`.
- GUI modules are loaded with `ug_require "::/gui/main/react.lua"`, `"::/gui/main/builtin.lua"`, etc. Our own modules use `require("<modId>::/path/file.script.tl")`.
- Lua limit: at most 200 locals in a file's main chunk, and each Teal record counts as one. Their tool failed to load at 201.

### Gizmo primitives (from `builtin.d.tl`)

- **`builtin.EdgeRenderable` works as a child of the tool's `ActionDescriptor`** (verified in game, next to the `ProposalViewer`). `builtin.EdgeRenderable{ edges = {...}, ignoreDepth = true }`, each edge `builtin.type.EdgeRenderable.Edge.new(g)` with `colors` (one `Vec4f` per end), `width`, `offsetZ` and `stepSize`. `g = api.type.EdgeGeometry.new()` with `type = api.type.EdgeGeometry.Type.STRAIGHT` (`g.straight = EdgeGeometry.Straight.new()`, `pos = {Vec2f, Vec2f}`) or `ARC` (`g.arc`: `center`, `radius`, `startAngle`, `angle`; `angle = 2π` draws a full circle), plus `height` (`Vec2f`, z at both ends), `tangent` (`Vec2f`, vertical), `length` and `width`. This is the gizmo layer, separate from the ghost.
- `ProposalViewerParam.controlPointInfo = Type.ControlPointInfo.new(pos, offsetZ, radius, State)`, with State Normal/Hover/Dragging/Idle. This looks like the game's own drag-handle marker. It allows one per viewer, so the PI handles probably need `EdgeRenderable` circles or HUD icons instead.
- `builtin.MissionArrowRenderable`, `api.gui.util.spawnEphemeralHudImage(...)`: fallback markers.
- Zoom: `api.gui.camera.getCameraData()` is a `Vec5f` {center x, center y, distance, angle, pitch}; a grab radius of 2% of the distance stays a constant size on screen.
- Dragging: the Selector's `onProcessMouseEvent` gets left `Pressed` and `Released`; returning true from `Pressed` keeps the game from acting on it, so a drag moves our handle and not the camera.
- Modifier keys: no mouse-event field; `api.gui.inputAction.modifierOnlyActionIsActive("IA_PRECISION_MODE")` is the only modifier-only action the game uses.

## Cant: leave it to Real Track Cant, optionally

The engine has no cant, and we don't compute any. **RTC is never a required dependency.** We build with the base track templates (never RTC's `_dvp` variants); a player who wants cant can upgrade the built track to RTC's canted track type, and RTC cants it from its curvature. Our curvature is a clean clothoid profile, so RTC's smoothing should behave well.

How RTC works, for reference: in `postRunFn` it generates variants of every track type (`_dvp` is the one the menu builds; `_dv`, `_dvs` and `_dvf` are internal). A game script watches `builder.proposalApply` and swaps segments to the right variant. It then places `devers_render.con` constructions with tilted models and rolls the trains. Its target cant is 0.8 × `11.8 V²/R` mm, capped at `40 + 0.46 V` mm (clamped to 60–200), and smoothed over `clamp(1.2 V, 40, 240)` m.

1. **Proposal smoke test.** From a game script event, build one hard-coded alignment (straight → spiral → arc → spiral → straight) as Hermite pieces between two new nodes. Check the dry-run cost and errors, then build.
   - Done, then removed: a game script (`tg_engine.script.tl`) built a hard-coded path from **TG dry run** / **TG build** buttons in the game bar. The tool now builds its own ghost.
   - `./check.sh` type-checks every `.tl` file (it symlinks `.tlpath/` so `tl` resolves `<modId>::/` requires) and runs `test/*_test.lua` offline.
2. **Port the core to Teal.** Vec, segment sampling (clothoids by Gauss–Legendre quadrature, as in Lean), corner solve and `buildPath`, plus a sampler that emits nodes every ~N m.
   - Implemented: `tg_geometry.script.tl` ports `Vec`, `Segment` (no RMF frames) and `Path` (no windings), keeping Lean's operation order. `tg_alignment.script.tl` samples a path into nodes `{x, y, heading, s, k}`: one at every segment boundary and evenly spaced ones in between, at most `step` apart. It drops a node closer than `MIN_PIECE` (1 m) to the previous one, so a zero-length straight between two corners never becomes a crash-sized piece. The smoke test now builds through three PIs ahead of the camera (350 m legs, 40° left) with the UI's design parameters. The grade is still linear between the terrain heights at the ends; elevation comes in milestone 5.
   - Test: `lake exe fixtures` (`Fixtures.lean`) runs `buildPath` over 10 PI fixtures and writes `test/fixtures.lua` with every float as its IEEE bit pattern. `test/geometry_test.lua` checks the port against it: every length, radius, speed, point, tangent and curvature is **bit-exact** (tolerance 1e-9). Regenerate the fixtures after changing the Lean core.
   - Verified in game: TG build lays the 693 m smoke path as 73 pieces and 74 nodes (147 entities). Cost 124,711, no errors or collisions.
3. **Tool skeleton.** Register the construction tool and pick the start and end segments as in Track Connector. Their ends fix the start and end headings.
   - Implemented: `tg_tool.res.lua` registers "Track Geometry" under Tracks → Tools. `tg_gui.script.tl` picks a free track end (one track piece, no road; the piece under the mouse or the nearest end within 40 m), then another. `tg_ends.script.tl` lays the starting PIs: straight if the second end is dead ahead and facing; else a lead PI 200 m out on each end's ray and a free middle PI halfway between the leads, so the middle leg runs near the straight line between the ends and the leads take the turn. On short spans a lead stops halfway to where the rays meet ("corner": they meet ahead of both ends, each leg 20 m to 3× the distance between the ends) or a third of the distance between the ends ("s-curve"). The first and last legs run along the ends' directions, so the path keeps both headings. The ghost (`ProposalViewer`) shows a 30 m stub at the end under the mouse, then the whole path from the start to the hovered end, joined to both existing nodes, with a linear grade between their heights. The tooltip shows the length, layout, cost and the game's errors. Right-click steps back; nothing is built yet.
   - `tg_proposal.script.tl` turns sampled nodes into a proposal (shared by the ghost and the smoke test). It can join the first and last node to existing nodes.
   - Test: `test/ends_test.lua` checks each layout's choice and that the sampled path starts and ends on the ends with their headings.
4. **Horizontal editing.** Add a turn at a spot on the alignment, drag turns over the terrain, and resize a curve with its brackets (per-turn budget). Draw the gizmos with `EdgeRenderable`.
   - Implemented: `tg_edit.script.tl` (no game API) holds the edited alignment: its PIs and per-PI budget overrides. A turn next to an end only slides along that end's ray, so the joins keep the ends' headings; a turn next to both ends (the corner layout) is fixed until another is added. Pressing on the track or a leg adds a turn there (it splits the leg without bending it, and the curves beside it keep their budgets) and grabs it; on the straight layout it adds three, so the middle one is free. Right-click on a free turn removes it; on anything else it does nothing (it never steps back while editing, which used to throw the whole alignment away when it missed a turn). Esc steps back. Dragging a bracket sets the corner's budget, from the `minRadius` floor up to the room its neighbours leave. The interaction is loosely based on the Lean UI, not ported from it.
   - Gizmos: the PI polyline, a circle at each turn (orange free, cyan on a ray, grey fixed), a tick across the leg at each curve's start and end, white under the mouse. While dragging, the gizmos follow every tick and the ghost lags behind: it is remade at most every `GHOST_TICKS` (4) tool ticks, and only once the game has checked the last one (its `onCreateProposalData` came), or after `GHOST_WAIT` (20) ticks. The game's check of each ghost is what made drags stutter; the old 0.2 s limit was measured with `os.clock()` (see GUI pitfalls) and so let a ghost through almost every tick. In vertical mode the sampled path is kept until the turns or curves change (`Edit.hrev`), not made every tick. Mod Lua has no threads (coroutines take turns on the one thread), so lagging behind is the only way to take work off a drag.
   - **Budget rule changed in the Lean spec** ("leg minus neighbour", `cornerLayouts` in `Path.lean`): a corner's own legs bound it by the whole shorter leg, not half. A leg whose far end does not curve (a path end or a straight PI) is the corner's alone; on a leg shared with another curve, a bracket goes up to where the neighbour begins. When the two asks do not fit (a moved PI shortened the leg), the leg is split in proportion, so the result does not depend on order. `buildPath` and the Lean UI's brackets use it; the default budgets are unchanged. Three new fixtures cover it (13 in all).
   - **End curves take all their room by default** (`cornerLayouts`): a corner next to a path end with no override asks for the whole leg to the end, and on its other leg the leg less the neighbour's own ask (override or `legBudget` share). So the first and last curves start on the track ends unless the other leg stops them, and the radius is as large as it can be. Such a corner only fills the room left, so it gives way: a neighbour's bracket may widen until the end curve reaches its `minRadius` floor. Once the player drags its own bracket it has an override and holds its size. Adding a turn leaves it automatic as long as it is still next to an end (other curves beside the split leg still keep their budgets as overrides). The curve can fill a leg exactly, leaving a zero-length straight that the sampler already skips. One new fixture covers it (14 in all).
   - A curve can now end exactly on a path end, leaving a zero-length final straight with no direction; `tg_alignment` skips zero-length segments so the end heading comes from the curve.
   - Test: `test/edit_test.lua` checks each edit, that the path still joins both ends along their headings, that no curves overlap, and the bracket bounds.
   - Verified in game: dragging turns and brackets, adding and removing turns, and the wider curves.
   - **The session** (`tg_session.script.tl`, no game API; test `test/session_test.lua`). Which step the tool is at, the picked ends, the edit and its mode, what is under the mouse and what is dragged, and what each click, right-click and "back" means. The GUI turns the game's callbacks into its events (`tick`, `mouse`, `click`, `back`), hands it what only the game knows as a `World` (the ground under the mouse, the grab radius, the snap and is-this-end-still-free functions), carries out the requests an event returns (open or close a window, ask to build, drop the ghost), and draws from its fields without writing them. Leaving the edit is one transition, whether by Esc or because an end went away.
   - **The edit** (`tg_edit.script.tl`, no game API; test `test/edit_test.lua`). The alignment being edited and its derived view: its own design params, and its path sampled every 10 m, made again only when the horizontal alignment changes (`hrev`). Callers read it in metres through it (`polyline`, `handles`, `corners`, `nodes`, `points`, `profile`), never its fields. Each turn holds its own curve size, so sizes stay with their turns as turns are added or removed. `hit` is what is under the mouse in either mode, one tagged value: a turn, a bracket or a leg (also where the track leaves the legs, on the nearest leg), or an elevation point or the track.
   - **The world** (`tg_world.script.tl`, all game API, no offline test). Every read of the game world: a track template's facts as one `TrackType` (menu name, top speed, grade limit, the bridge and tunnel types the game's menu would pick), cached per template and year; the template to build from the menu settings (`templateFor`, the wired version when Electric is on); the ground and water at a point; and the track ends (is a node still there, the free end at a node, `joinable`, the free ends near a point). It holds the crash traps (never ask the street system about a non-node; never hand the game a proposal naming a node that is gone or no longer free). Every read is guarded and never raises; a failed track type lookup gives the defaults, is not cached and is logged once per template. Which end the mouse snaps to is a pure rule in `tg_ends.snap` (test `test/ends_test.lua`). `tg_proposal` only makes proposals.
   - **The plan** (`tg_plan.script.tl`, no game API; test `test/plan_test.lua`). Everything the ghost shows and the tool builds, from the ends and the edit: the path every 10 m (`dense`, what the ground check and the readout read) and the long pieces handed to the game (`built`), with heights, grades and each piece's kind. The GUI hands it the ground and water as functions, makes the proposal from `built`, and gives the plan the game's per-piece speeds when they come (`readout`). An elevation point always gets a node of its own (a bridge or tunnel end within 1 m of it moves there).
   - **Speed and grade readout** (`tg_readout.script.tl`, no game API; test `test/readout_test.lua`). The game's Speed Limit layer paints only built track (its `SpeedLimitsColor` painter walks the transport network), so it never colours the ghost. But the ghost's `ProposalData.entity2tn` holds the transport network each proposed piece would make, keyed by the proposal's entity ids (pieces `-1..-m`), and each network edge has the game's own `curveSpeedLimit` (m/s, from the curve alone, before the track type caps it). Found in the Gleis- und Straßenbauanzeige mod (mod.io `6418902`, `preview.lua` `curveSpeedLimit`); verified in game (536 of 536 pieces). The tooltip shows the slowest curve limit and where, the grade range and the smallest radius, instead of the old list of segment kinds. Colouring the path by speed or grade (`EdgeRenderable`, v27) was tried and dropped: not useful.
   - **Curve badges**, like the track builder's own: one per curve at its arc's middle, with the game's slowest curve limit over the curve (km/h) and the grade there, using the builder's icons (`gui/construction/build_control/symbol_speed_16`, `symbol_slope_-4..4_20`). The path's slowest curve is pink. They are drawn by a `builtin.FullScreenComponent{ recipe, param }` among the tool's `ActionDescriptor` children (as the town window shows its layer legend): a mouse-transparent `FloatingLayout` with a `FloatingLayoutChild{ h, v }` per badge, stretched over the screen by `tg_gui.css.lua` (`gravity = {-1, -1}` on `R::TgBadges` and its `FloatingLayout`; any `*.css.lua` in the mod is loaded, as in Track Connector's `tc_gui.css.lua`). Left alone the layout shrinks to its badges and they all pile up at the left middle of the screen (v28); a `size` in its own `meta.styleSheet` is ignored (v30), and inline styles have no `gravity`; the full-screen recipe must return a layout: a `Component` there kills the GUI with "Recipe child must be a layout" (v29). The badges come with the ghost's data, so while dragging they trail it. There are no text HUD primitives: `HudIconManagerConfig` follows entities and `spawnEphemeralHudImage` draws images only.
5. **Vertical editing.** Elevation points placed along the chainage, with editable heights. A side window switches between horizontal and vertical editing.
   - **How the game's builder eases grade** (reverse engineered from the stripped binary via assert strings; `UI::StreetBuilder::CreateProposalAndUpdate` @ 0xe56200, curve @ 0xe40f50, `CalculateInitialTangent` @ 0xe3ebc0): one cubic Hermite for the whole drag, then cut into pieces. The start grade s0 is the existing edge's 3D tangent; the end grade e is picked so the curvature vanishes at the far end: `z'(u) = e + (s0 − e)(1 − u)²`, mean grade `(s0 + 2e)/3` (the 2/3 is hardcoded). 9 % into a 0 % drag over four pieces gives 6.9 / 3.6 / 1.3 / 0.2 %, as seen in game. No vertical-curve minimum. Track templates: `maxSlopeBuild = 0.085` (the incline slider), `maxSlope = 0.13`, `maxSlopeShape = 0.16`; Realistic Track Gradients (mod.io `6433559`) sets `maxSlopeBuild` to its chosen limit (default 40 ‰).
   - **Profile** (`tg_profile.script.tl`, no game API; test `test/profile_test.lua`): a clamped cubic spline in chainage through the elevation points, the ends included. The end grades are the existing tracks' grades (read from the end edge's tangent z), so the joins have no kink. Between points it is the cubic Hermite with their heights and grades; the interior grades are solved (tridiagonal, Thomas) for a continuous second derivative. With no interior points it is one Hermite from end to end. It may overshoot a point slightly; accepted. Not specified in Lean (not worth maintaining). Each node gets its height and grade from it, and each piece's tangent z is grade × T at its own end.
   - **Editing** (`tg_edit`, test `test/edit_test.lua`): elevation points are kept as a share of the length and a height, so they follow horizontal edits. Adding one puts it on the profile as it is; it stays `MIN_SPAN` (20 m) from its neighbours and the ends. A move stops where the steepest grade at the nodes would pass the limit (bisection along the move); a profile already past it may move without getting steeper. The limit is the template's `maxSlopeBuild` (`tg_world.trackType`).
   - **GUI** (untested in game): picking the second end opens a `builtin.Window` (`TgModeWindow`, `addSingletonWindow` from the click, as the confirm window) with a `ToggleButtonGroup`: horizontal or vertical alignment. It has class `no-close-button` (the plain surface; the default one has a notch for the close button) and id `tgmode`, which `tg_gui.css.lua` gives a `minSize` so the title fits, and places at the bottom right above the game bar (`anchorPoint`/`gravity` `{1, 1}`, `margin`, as the game's `Window#calendar`). In vertical mode a press on the track adds an elevation point and grabs it; a drag slides it along the track (the mouse's ground point projected on the path), Shift (`IA_PRECISION_MODE`, as Move It reads it) at the press drags its height instead, from the mouse's screen y (mouse events' `y`) at `HEIGHT_PER_PX` × camera distance per pixel. Right-click removes the point under the mouse. Gizmos: a circle on the ground and a post up to the track at each point (grey at the ends). Badges: height and grade at each point, grade halfway along each span (`readout.profileBadges`).
   - Verified in game: the mode window (after the wrapper fix), adding and dragging elevation points.
   - **More badges**, as the game's builder badges each piece it lays: every `BADGE_EVERY` (50 m) along the path, speed and grade in horizontal mode (`readout.alongBadges`), grade in vertical mode (`profileBadges`' "grade"). `placeBadges` places curve and point badges first, then spans, then these, and skips any that would overlap one already placed on the screen (badge box about `BADGE_W` × `BADGE_H2`/`BADGE_H1` px), so they thin out when zoomed out.
   - Started with bridges and tunnels. A proposal takes each piece's `comp.type` literally: the game's drag tool decides bridges and tunnels inside the native `StreetEdgeBuilder` (for track, `bridgeMinHeight` = bridge height 6 + 6, `tunnelMinHeight` = tunnel height 9 + 6; roads use 6 + 5 for bridges; `construction_react_util.tl` ~L3257), which we cannot feed our geometry. So `tg_structures.script.tl` (no game API) classifies each piece by its mean clearance over the ground: bridge if over water (`api.engine.terrain.isOnWater`) or more than 12 m above, tunnel if more than 15 m below. Short ground between two runs of the same kind (up to 40 m) joins them; a run under 20 m becomes ground, unless it crosses water. The types are picked as the game's menu auto-selects them (`menu_category_util.getAvailableObjectsSorted` + `makeFilterObjectsFn`): on offer this year, carrying RAIL, the slowest speed limit at least the track's, else the fastest. Bridges: `::/infrastructure/bridge/*.bridge` (stone always, concrete from 1970, ...); tunnels: `tunnel_a` (rock), `tunnel_b` (concrete, from 1970). Test: `test/structures_test.lua`.
   - The tooltip now shows all of the ghost's errors and warnings and how many things it runs into, not just critical errors; they are logged once per path (not while dragging).
6. **Ghost and build.** `ProposalViewer` with the sampled proposal shows cost and errors. While editing, a left click that grabs nothing (off the path and its handles) opens a confirm window. It refuses, with the reason in the tooltip, while the game is still checking the ghost, when the game refuses it (critical), when the game lists any error messages for it (warnings and collisions do not block), or when it costs more than the player has. A failed build shows in the tooltip.
   - **Confirm window**, as in Track Connector (`openConfirm` in `tc_gui.script.tl`): `dialog_react_util.DialogWindow` through `params.gameCtx.windowContainer:get():getApi()` (`addSingletonWindow`, `removeAllWindows`), with Build and Cancel (`onBackChoiceIndex = 2`, so Esc cancels). It shows the path line, the readout summary, the ghost's warnings and the cost. The text is wrapped by hand to 80 columns. **Build** sends the ghost from when the window opened with `makeWorldBuildProposalCmd(ghost, context, false, true)` straight from the GUI, after checking both end nodes still exist, and the tool starts over. While the window is open, the tool ignores map clicks and leaves "back" to the window. The click that closes it is ignored for 2 ticks, so it does not open the window again. Closing the tool closes the window. If the window cannot open, nothing is built. Verified in game.
7. **Track type.** The menu entry has two settings, as Track Connector's: **Track**, an icon picker (`getFilterObjectsFn`) over the track templates on offer this year without overhead wires (`menu_category_util.getAvailableObjectsSorted`, `roadType == TRACK`, no `catenaryRemove`; default standard), and **Electric** (Off/On), which swaps in the type's `catenaryAdd`. They sit in the Settings window (`location = Default`): a custom tool's `getCurrentParams` only returns those. The tool reads them every tick (`readTemplate`); the template is part of the ghost key, so changing it remakes the ghost, and the track speed (readout, bridge and tunnel types) and grade limit follow it. The confirm window names the type. Untested in game.

Out of scope: editing existing track, re-editing after a build, following the terrain, computing cant ourselves, depending on RTC, an undo tree, loop winding.

## Trying a change in game

Run `./check.sh`, then `./sync.sh`, then reload the map (load the save again); there is no need to restart the game. The game reads the mod only from the staging copy, when a map loads, so an unsynced change looks like a bug in game.

## GUI pitfalls (found during milestone 4/5 testing)

- **`os.clock()` is CPU time summed over the game's threads, not wall time.** On a busy map 0.3 "s" passes in tens of ms, so it is useless for short windows. The right-click windows count tool ticks instead, and whether the tool is still ticking counts frames (`TgProbe`'s `onStep` counts every frame; the tool is live while its last tick was at most `LIVE_FRAMES` (60) frames ago).
- **Restricted outside a game-bar plugin's `react.onStep`:** `api.gui.mouse.getTerrainPosition` and `api.gui.camera.world2Screen` ("API is currently restricted" in the tool's timer). `api.engine.terrain.getHeightAt` and `isOnWater` work in the GUI.
- **The native tick/cross next to the track builder's tooltip is `BuildControlComp`** (C++, used by the track/road builders only; not in any tealdef or GUI script). Its icons are in `gui/construction/build_control/` (`symbol_check_20`, `symbol_x_20`, `symbol_bulldozer`).
- **A window recipe must wrap `builtin.Window`** with `react.RegisterWrapperRecipe(name, builtin.Window, fn)`, as every window in the game does (`DialogWindow`, `EntityWindow`, ...). The first mode window was a plain `RegisterRecipe` returning `builtin.Window`, opened from a click, and failed the same `NodeStorage.cpp:51` assertion while transforming `WindowContainer` as the `onStep` window below; that one may have had the same cause. `ToggleButtonGroup` indices are 1-based (`initialSelected = 0` logs "0 does not do anything").
- **Opening a window from `onStep` crashes the game.** `gameCtx.windowContainer:get():getApi().addWindow(...)` (the container the construction menu uses for its params window) called from the game bar's `onStep` failed a native assertion (`NodeStorage.cpp:51`, "While transforming … WindowContainer") right after opening, twice. The game itself opens windows from `react.onMount` of a mounted component; that is untested. Construction-menu `params` are option switches only (Button/IconButton groups, Slider, ComboBox, CheckBox), with no one-shot button.
- **Removal stays on right-click** (it acts only on the turn under the mouse). Still to do: a linear undo stack of edit snapshots, so Esc out of editing does not lose the alignment either. The alternatives that were considered: a panel opened from `react.onMount` of a keyed component (may crash like the `onStep` window), or an Edit / Remove mode switch in the tool's toolbar (`location = Toolbar`, safe).

## Open questions

- Vertical profile is **not in the Lean spec**, by choice: `buildPath` solves corners in 3D (tilted corner planes), but the mod runs horizontal PIs through it at z = 0 and lays the profile (`tg_profile`) on top.
- **Piece length (adaptive sampling).** A Hermite with `T = 4r tan(φ/4)` follows the curve closely even over long pieces: on a tight corner (R 134 m) a 31 m spiral piece is 0.16 mm off, a whole 77° arc as one piece 14 mm (measured offline against the true curve). So the ghost no longer builds 10 m pieces. The path is still read every `STEP` (10 m) for bridges and tunnels, the readout and picking, but it is built in pieces of at most `MAX_TURN` (15°) of turn with no length limit: a straight is one piece. There is a node wherever a bridge or tunnel starts or ends and at every elevation point, so each piece is one kind and lies in one span of the profile, where its Hermite z matches the spline. The structure kinds carry over from the dense pieces (`structures.changes`, `alignment.carry`); the game's curve limits per built piece carry back onto the dense pieces for the readout. Edges (`SegmentAndEntity`) are only ever Hermites (positions and tangents); `EdgeGeometry` ARC is for drawing (`EdgeRenderable`) only. Verified in game: much faster, long edges (straights of hundreds of metres as one piece) build and behave fine, and the transitions look right.
