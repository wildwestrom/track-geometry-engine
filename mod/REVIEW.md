## 1. Structure at a glance

Layers, from the bottom (each uses only the layers above it in this list):

```
1. geometry                       path maths, no deps
2. alignment, profile, ends,      sampling, vertical profile, picked ends,
   speedprobe                     the game's curve speed on a radius
3. structures, crossings, readout bridges/tunnels, crossings, tooltip text
4. edit                           PIs and curve sizes being edited
5. layout, plan                   path -> native game proposal
6. world                          reads the game world (game API)
7. session, proposal, gizmos      tool state, ghost lifecycle, shapes to draw
8. gui                            wires everything to the game (game API)
```

(Simplified: a few modules also reach a layer or two down. Check each file's `require` lines.)

Pure modules (no game API, tested offline in `test/`): everything except `world` and `gui`.

Data flow: the player picks two ends (`session`), then edits PIs (`edit`). `plan` builds the path (`geometry`, `alignment`, `profile`), classifies bridges and tunnels (`structures`) and finds crossings (`crossings`). `layout` turns that into a native game proposal. `proposal` manages the ghost's lifecycle. `gizmos` and `readout` describe what to draw. `gui` wires it all to the game.

## 2. Pure maths layer (no game API)

- [ ] **`tg_geometry`** (487 lines): the core. A port of the Lean spec, with straights, arcs and transition spirals. Check it against `test/geometry_test.lua` and `test/fixtures.lua`. Fixtures are generated by `lake exe fixtures` from the Lean code, which lives outside `mod/`.
- [ ] **`tg_alignment`** (150): samples a path into nodes, each with a position and heading. Look at the Hermite tangent length and the `step`/`maxTurn` limits.
- [ ] **`tg_profile`** (121): vertical profile, a monotone cubic (PCHIP-like) through elevation points
- [ ] **`tg_ends`** (509): turns a picked end (free track end, node, point along a piece, ground) into a point and a direction, and builds the starting alignment between two ends
- [ ] **`tg_speedprobe`** (106): the game's curve speed on a radius, for the mode window's Curve section. The GUI hands in a dry run of a test arc (`measure`); this caches the answers, remembers when the game can't answer, and searches for the radius a speed needs (to 0.25 %, up to `MAX_RADIUS` 20 km)
- [ ] **`tg_structures`** (155): classifies pieces as bridge, tunnel or ground, using thresholds copied from the game, and tidies short runs
- [ ] **`tg_crossings`** (289): finds where new track crosses existing streets or track, so they can share a node. Mostly intersection geometry, so a likely place for edge-case bugs.
- [ ] **`tg_readout`** (393): tooltip lines and the badge at each curve (speed, grade)

## 3. Editing and planning

- [ ] **`tg_edit`** (1016): the edit model. Turns (PIs), curve size brackets, and the move/add/remove rules with their constraints at ends that have a heading. Large, so read it in two sittings.
- [ ] **`tg_layout`** (475): builds the native proposal, with edges numbered `-1..-m` and nodes `-(m+1)..`. Handles switches, which replace the pieces at a node, and cuts. Read the NOTES.md section "Building track (proposals)" first.
- [ ] **`tg_plan`** (214): the glue. It makes a `dense` path (for reading the ground) and a `built` path (the pieces handed to the game).

## 4. State machines

- [ ] **`tg_session`** (778): the tool's step (pick start, pick end, edit), the click/right-click/back meanings, and the events the GUI feeds in. The GUI reads its fields and never writes them, so check that this holds.
- [ ] **`tg_proposal`** (638): the ghost lifecycle: when to remake it, the game's check results, rounds that clear town buildings, and the build gate
- [ ] **`tg_gizmos`** (308): the shapes to draw (circles, brackets, polylines), their order, height and colour role

## 5. Game-facing code (the riskiest part)

- [ ] **`tg_world`** (525): everything read from the game, namely track types, ground and water, and track ends. It encodes **crash avoidance** (asking the street system about a non-node kills the game, and a proposal naming a missing node kills it). Check that every call goes through the guards.
- [ ] **`tg_gui`** (2027): the React-style GUI plus the tool, probe and menu plugins. By far the biggest file. Its own header lists the parts, so split your reading along those. Read NOTES.md "Tool and GUI" and "GUI pitfalls" first.
  - [ ] imports, the clock, tool state, track type
  - [ ] geometry mode: the "Track Geometry" and "Alignment" (horizontal/vertical) rows' state, ghost and proposal handling, build
  - [ ] the mode window (incl. its Curve section) and the confirm window
  - [ ] editing, and editing the vertical alignment
  - [ ] the session's adapter: game callbacks into session events, and the `speedprobe` source (dry-run test arcs)
  - [ ] curve badges
  - [ ] gizmos: rendering (`EdgeRenderable`), colours, and the tool (`toolAction`)
  - [ ] the game's track builder (`TgMenuPlugin` and its rows)
  - [ ] bottom bar (`TgProbe`: per-frame ground read and badges)
